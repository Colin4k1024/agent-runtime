# 全集团 Agent Runtime 演进架构与路线图

本文面向将 openJiuwen Agent Runtime 从当前试点运行时演进为全集团级 Agent 托管平台的场景，梳理当前架构事实、真实能力差距、目标架构、关键架构决策、分阶段路线图和验收标准。

## 1. 结论

当前 Runtime 的定位正确：把 Agent 从开发态发布为可在线调用的运行服务，并提供基础生命周期管理。但按全集团托管平台标准评估，当前版本仍处于“单机 / 小规模 / 低码 Agent 试点运行时”阶段，尚未达到“多租户、高可用、可治理、可观测的集团级基础设施”标准。

核心差距集中在：

- 身份认证与租户隔离；
- 统一流量入口；
- 声明式状态治理与故障自愈；
- 标准化工件与 K8s 化部署；
- 可观测性、审计、配额与成本治理；
- 发布、升级、回滚与灰度能力。

因此，不建议直接横向扩容当前 subprocess 架构。推荐演进方向是：

```text
部署进程的服务
    ↓
声明式 Agent 托管控制面
  + 统一流量面
  + 标准化工件
  + 可观测治理体系
```

## 2. 当前架构事实

### 2.1 当前主链路

当前部署链路为：

```text
Client
  ↓
Runtime Server
  ├─ 保存 Agent IR
  ├─ 写 deployment 记录
  ├─ 选择 DeployMode
  ↓
DeploymentManager
  ├─ subprocess
  ├─ docker
  └─ k8s
  ↓
Agent 进程 / 容器 / Pod
  ↓
Client 直接调用 Agent URL
```

### 2.2 已验证能力

本地验证表明以下能力可用：

- Agent 配置上传；
- deployment 记录创建；
- subprocess 策略执行；
- 独立虚拟环境创建；
- Agent 进程启动；
- Agent `/health` 探活；
- Runtime list / detail 查询；
- Agent `/agent_detail` 查询；
- `/query` SSE 事件流框架。

### 2.3 当前限制

#### REST 主链路绑定低码 Agent

当前 subprocess 部署器在存在 `ir_path` 时固定启动低码 Runner。因此 HTTP 主链路当前不是通用 Agent 托管，而是低码 Agent Runtime。CLI 可以部署本地 WHL，但 REST 主链路尚未开放同等能力。

#### 没有统一流量面

部署成功后，Runtime 返回 Agent URL，客户端直接调用 Agent。Runtime 不在业务流量路径上，因此无法统一做认证、授权、限流、配额、审计、熔断、灰度路由、请求追踪和租户级计费。

#### 状态真相分散

当前状态来源包括：

- `deployment` 表；
- `process` / `docker` / `k8s` 策略表；
- 部署器内存中的进程和端口状态；
- 实际进程、容器或 Pod 状态。

这些来源之间缺少持续 reconciliation，Runtime 重启或 Agent 异常退出后，数据库状态可能与真实状态漂移。

#### 单 Agent 资源成本高

本地实测单个成功部署的虚拟环境约 712MB，依赖包约 193 个，冷启动为分钟级。按此模型推算，100 个 Agent 仅虚拟环境磁盘就接近 71GB。该资源模型不适合集团规模。

#### 失败部署缺少清理

本地验证中，安装失败后的 deployment 会留下失败的虚拟环境目录，且安装失败后仍会继续尝试启动 Agent。这暴露出 `pip_install()` 返回值未检查、失败资源未回收、失败原因未结构化落库的问题。

#### 多租户不是安全边界

当前租户信息主要来自客户端 Header，没有认证和签名。虽然列表接口有租户过滤，但 detail、delete、stop 等接口尚未形成完整租户边界，存在跨租户访问风险。

#### 安全能力未接入主链路

仓库已具备 Ed25519、信封加密、证书管理、link-auth、nonce 防重放和 pin store 等安全原语，但管理 REST API 尚未接入这些能力。当前状态是“安全原语存在，安全架构未接线”。

#### 发布治理缺失

当前只有 deploy、list、get、delete，缺少版本管理、升级、回滚、灰度、蓝绿、金丝雀、发布审批、发布历史、配置 diff 和发布锁。

### 4.2 三个平面

#### 管理面 Control Plane

负责 Agent 注册、工件上传、版本管理、部署申请、发布策略、回滚、状态查询和权限审批。

#### 数据面 Data Plane

负责真实业务流量，统一入口为 Runtime Gateway。Gateway 承担认证、租户校验、限流、配额、路由、追踪、审计、SSE 代理、熔断和会话路由。

#### 治理面 Governance Plane

负责审计、配额、成本、安全策略、合规、熔断、黑白名单和平台运营。

## 5. 核心架构决策

### 决策 1：Runtime 必须同时包含控制面和数据面

- Evidence：当前 Runtime 只负责部署，不承接业务流量，导致无法统一治理。
- Reasoning：全集团平台需要统一认证、审计、限流、配额、追踪和计费。如果客户端直连 Agent，这些能力需要在每个 Agent 内重复实现。
- Implications：需要新增 Runtime Gateway，并保持 AgentApp 契约不变。

### 决策 2：生产默认运行时应切换为 Kubernetes

- Evidence：subprocess 模式可用，但单 Agent 资源成本高、冷启动慢、无自愈、无弹性伸缩、无标准资源隔离。
- Reasoning：全集团需要声明式部署、健康探针、自动恢复、滚动升级、资源配额、网络隔离和多副本调度。
- Implications：subprocess 保留为开发模式，Docker 作为过渡模式，K8s 成为目标生产模式。

### 决策 3：Agent 交付物统一为不可变 Artifact

- Evidence：当前 IR、WHL、镜像三种路径并存，行为不一致。
- Reasoning：部署系统需要稳定、可审计、可回滚的交付单元。
- Implications：所有 Agent 最终转为带 digest 的 Artifact，部署记录引用 digest，回滚即切回历史 digest。

### 决策 4：租户身份必须在 Gateway 认证后注入

- Evidence：当前 Header 可伪造，且部分接口存在跨租户访问风险。
- Reasoning：租户边界必须建立在可信身份上。
- Implications：删除对客户端身份 Header 的直接信任，所有 API 增加认证，所有数据访问强制 tenant scope。

### 决策 5：状态必须由 Controller 收敛

- Evidence：当前 DB 状态与真实进程状态可能漂移，Runtime 重启后无恢复逻辑。
- Reasoning：托管平台的核心承诺是系统最终处于用户期望状态。
- Implications：需要实现启动时全量 reconcile、周期性 reconcile、事件驱动 reconcile、状态修正和孤儿资源清理。

### 决策 6：Secret 不应通过明文环境变量传递

- Evidence：当前 userdata 通过环境变量注入，适合本地验证，不适合集团生产。
- Reasoning：环境变量容易泄漏到进程列表、日志、core dump、子进程和诊断工具。
- Implications：生产模式应接入 KMS / Vault，并支持短期凭证、按需挂载、访问审计和自动轮换。

## 8. 落地路线图

路线图按能力阶段划分，实际周期需结合团队规模和公司基础设施成熟度调整。

### Phase 0：止血修复当前主链路

目标：让当前版本成为可信试点，而不是继续扩大技术债。

周期估算：2~3 周。

必做事项：

1. 修复 `pip_install()` 返回值检查；
2. 失败部署自动清理进程、虚拟环境和临时目录；
3. detail、delete、stop 增加租户过滤；
4. API 错误码规范化；
5. API 返回补齐 port；
6. Runtime 启动时执行 deployment 状态收敛；
7. 引入最小 JWT 或 service token 认证；
8. 管理操作写 audit event；
9. 建立统一 Gateway 初版；
10. 为以上能力补自动化测试和 CI。

验收标准：

- 安装失败不启动 Agent，不留虚拟环境，状态为 failed；
- 跨租户 detail / delete 被拒绝；
- 端口占用返回 400；
- Runtime 重启后 running 状态重新校验；
- 核心链路单测稳定通过。

### Phase 1：安全试点版

目标：让一个部门可以安全试点。

周期估算：4~6 周。

必做事项：

1. 接入 OIDC / SSO 和 JWT 校验；
2. 建立租户、workspace、actor 模型；
3. 增加全操作审计；
4. 增加 Runtime Gateway 初版；
5. Secret 从 KMS / Vault 拉取并注入；
6. 统一结构化日志；
7. 建立 CI 门禁。

验收标准：

- 所有 API 有认证；
- 所有资源访问有租户边界；
- 所有管理操作有审计；
- 业务流量经过 Gateway；
- 核心链路 CI 通过。

### Phase 2：生产化 K8s 版

目标：从“能跑”升级为“可托管”。

周期估算：8~12 周。

必做事项：

1. 定义标准 Agent Artifact；
2. 建立构建流水线；
3. 实现 K8s Operator 和 CRD；
4. 配置资源隔离、NetworkPolicy、PodSecurity；
5. 实现 HPA / KEDA 和 warm pool；
6. 实现版本、回滚和灰度；
7. 接入 OpenTelemetry、Prometheus、集中日志和告警。

验收标准：

- K8s 为默认生产部署模式；
- Agent 交付物不可变；
- 支持版本回滚；
- 支持健康自愈；
- 核心指标完整；
- 失败资源自动回收。

### Phase 3：集团级平台版

目标：支持多 BU、多租户、大规模、高可用。

周期估算：一个季度以上。

必做事项：

1. 建立配额与成本治理；
2. 实现控制面和数据面高可用；
3. 支持多集群、区域路由和灾备；
4. 建立安全合规和策略引擎；
5. 建立平台运维能力。

验收标准：

- 支持多 BU 隔离；
- 支持高可用；
- 支持配额与成本；
- 支持审计与合规；
- 支持多集群治理。

## 11. 主要风险

### 风险 1：继续放大 subprocess 模式

如果继续以 subprocess 为主，会遇到磁盘成本线性膨胀、冷启动慢、无自愈、无标准资源隔离、无法滚动升级和无法做集群级调度。subprocess 可以保留为开发模式，不能作为集团生产主模式。

### 风险 2：只加功能，不建状态治理

如果没有 reconciler，只增加 API 功能，平台会越来越复杂，状态漂移越来越严重。必须先建立 desired state、observed state 和 reconciliation loop。

### 风险 3：安全后补

如果先做规模，再补安全，代价会非常高。多租户边界、Secret、审计和权限应随第一阶段一起完成。

### 风险 4：session 包过早接入主链路

`management/session` 的方向正确，但当前仍存在稳定性问题。应先修复并稳定，再作为 Gateway 的调度内核接入，不要直接放入生产主链路。

### 风险 5：Runtime 边界扩大化

Runtime 的边界应是托管、运行和治理，不应承担 Agent 编辑、复杂工作流设计、模型管理和知识库管理。这些能力应留在 Studio 或其他平台服务中，通过标准接口对接。

## 12. 最终建议

当前项目不应废弃，架构方向有价值，但需要一次明确升级：

```text
当前：
部署进程 + 返回 Agent URL

目标：
标准工件 + 声明式部署 + 统一网关 + 状态自愈 + 安全租户 + 可观测治理
```

推荐路线：

```text
Phase 0  止血，修失败处理与租户漏洞
Phase 1  安全试点，加认证、审计、Gateway
Phase 2  K8s 生产化，标准工件、Operator、回滚、观测
Phase 3  集团平台化，配额、成本、多集群、合规
```

关键判断：

```text
不要先横向扩容当前 subprocess 架构。
先补安全、状态、工件和流量治理。
否则规模越大，治理成本越高。
```
